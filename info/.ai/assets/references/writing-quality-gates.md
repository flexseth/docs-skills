# Writing

**Required** 

When writing, reviewing, or editing content, always write for the WordPress user in mind. At this point in the process, you should have issue context from GitHub, and understand the canonical document in question. With this knowledge, you should be able to determine if the user is an end-user or developer. 

You will remember the WordPress Brand Writing Style Guide, and these important sections:



Given context, you should know about who the end user will be, based on the type of documentation and the intended audience.

 [WordPress Marketing Style Guide](https://github.com/WordPress/marketing/blob/main/shared/references/wordpress-brand-writing-style-guide.md), paying specific attention to capitalization, proper nouns, voice and how to address the audience appropriately. The shortened version of this guide should be consumed as a quick reference for writing - do not read the entire guide.



**End-User Documentation**
Documents that are user facing should follow this principle. 
User facing documents are found at wordpress.org/documentation, aka the official WordPress documentation site, or "HelpHub."

**Technical Documentation**

For developer documents, use the WordPress [Docs Style Guide](https://make.wordpress.org/docs/style-guide/welcome/highlights/) for Technical Writing. Specific considerations for code, command-line syntax, etc, are [outlined](https://make.wordpress.org/docs/style-guide/welcome/highlights/#developer-content) in this style guide. This style should be applied to all developer-facing documentation within the WordPress project. This documentation lives on `developer.wordpress.org`. 

[Harper](https://writewithharper.com) is highly encouraged to use in your writing.

## Correctly Addressing Updates

Sometimes the docs update contributor addresses contributors by saying "This is X, This is Y" - however, their comments don't solve bring us any closer to a docs update. One such example is when the user mentions "screenshots need update" or "screenshots are hotlinked from Google" - but they do not upload screenshots for modification.

Additionally, this same user will still not have the permissions needed to update the correct screenshot. So the bottleneck once again is on the docs contributor who essentially has to go through and do the work again.
