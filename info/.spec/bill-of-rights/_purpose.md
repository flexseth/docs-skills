# Purpose

- **Problem:** Docs drift between WordPress releases. Only users with `Editor` access can change HelpHub (wordpress.org/documentation) or DevHub (developer.wordpress.org), so small fixes pile up. There are other docs updates such as Dev Notes and Release Notes, as outlined in the Release Team Leads doc. Currently, the Documentation Issue Tracker (DIT) has 469 open issues, a median age of 805 days, and 87% have had no human comment in 180 days (`TRIAGE.md`), showing the need for a better way to cohesively update docs.
- **Proposed flow:** A "proxy" fetches a page's raw block markup (represented as HTML) → a Playground blueprint recreates the post → a contributor edits in Gutenberg (Harper checks spelling and grammar; Notes carry the checklist) → Playground's PR feature allows the user to open a PR → the Docs Team reviews → an Editor applies it. GitHub gives the audit trail that WP.org revisions lack (`~/docs-updates-proposal.md`).
- **Roles:** Human (Seth, `@flexseth`) decides. Spec Kit plans and manages tasks during SDD, but hands off to Claude for planning and implementation. Claude plans, implements, and runs security review (`README.md`). More roles are detailed in the `/user-stories-and-journeys` directory, these roles are for the implementation flow and represent some real world docs updates scenarios.
- **Side quest but important:** A showcase for spec-driven development in the WordPress ecosystem, to solve a problem.
