# Rubric 06: Block Visibility Rules (JS Hooks)

The prompt describes outcomes only and names no APIs. Score whether the code chose correct, current WordPress APIs. Give full credit for an equivalent current API, and 0 for a deprecated, legacy or invented one. Name what was used in each reason.

## Expected doc surfaces
- Complex: `@wordpress/hooks` (`addFilter`, `applyFilters`, `doAction`) and the block filters reference
- Non-general: `editor.BlockListBlock`; `register_block_type_args` for all blocks; `wp_timezone()` / `current_datetime()`
- `blocks.registerBlockType`, `editor.BlockEdit`, `createHigherOrderComponent`, `hasBlockSupport`
- RadioControl / SelectControl, DateTimePicker, InspectorControls
- `render_block` filter, `enqueue_block_editor_assets`

## Criteria (1 point each unless noted)
1. Attribute added to all blocks with an `addFilter( 'blocks.registerBlockType', … )`, skipping core/freeform, with type and default.
2. Sidebar control via an `editor.BlockEdit` HOC (`createHigherOrderComponent`) with InspectorControls.
3. Choice control for rule type; date/time pickers only for the date range.
4. Editor outline added via `editor.BlockListBlock` (className or wrapperProps), not by global CSS on every block.
5. Editor stylesheet provided and enqueued.
6. Other plugins can add rule types through a JS filter (`applyFilters`) that builds the choices.
7. A JS action (`doAction`) fires when a rule changes.
8. Attribute also registered in PHP for all blocks (`register_block_type_args`), so server rendering accepts it.
9. `render_block` filter returns an empty string when the rule fails.
10. Logged-in check with `is_user_logged_in()`; dates compared in the site timezone (`wp_timezone()`, `current_datetime()` or `wp_date()`).
11. A PHP filter (`apply_filters`) lets others override the decision.
12. Editor assets enqueued with the asset file's dependencies and version.
13. No invented or deprecated APIs (2 points: deduct 1 per instance, minimum 0).

Max: 14
